# BatteryTray 如何读取各类设备

[English](../en/how-it-works.md) · [Русский](../ru/how-it-works.md) · **中文**

[BatteryTray](../../README.zh-CN.md) 无需厂商软件即可读取电量：它通过 USB HID（Windows 上用 Win32，Mac 上用 IOKit）以设备自己的协议与每个设备的接收器或数据线通信，蓝牙设备则直接使用系统已知的电量。它只询问电量，从不向设备写入任何设置。下面的每种协议都参考了记录该协议的开源项目，这些项目列在各行和 [THIRD_PARTY_NOTICES.md](../../THIRD_PARTY_NOTICES.md) 中；设备列表见 [devices.md](devices.md)。

## 协议

| 来源 | 协议 |
|---|---|
| `providers/barracuda.rs` | 通过接收器发送 Airoha RACE 命令：把接收器切换到 remote 模式，询问电压（`GET_BATTERY`），再切回 local 模式（移植自 [razer-barracuda-x-battery](https://github.com/mehdibouchami/razer-barracuda-x-battery)）。另外还有耳机自己发出的通知（类型为 `0x08` 的 RACE 帧，载荷 `[id 02 01 值]`）：`0x20` 耳机开/关，`0x21` 耳机自己的电量百分比，`0x2A` 数据线插入/拔出——这些是通过监听接收器发现的。充电结束：保持 4.20 V 之后，在数据线仍插着时电压降到 4.18 V 以下。 |
| `providers/rongyuan.rs` | 在接口 2（vendor page `FFFF`）上发送特性报告 `[00 F7 …]`，回复为 `[00 canRead kbBattery mouseBattery kbOffline mouseOffline …]`，来自 ATTACK SHARK 官方网页驱动。插着数据线的鼠标（同一驱动中的 32 个 USB ID）会接管失去它的接收器槽位。有些接收器 ID 被多个品牌共用，而回复中没有鼠标名称，所以名称取自接收器的产品字符串。 |
| `providers/xenta.rs` | 不发送任何内容：在接收器 usage page 为 `000A` 的集合（接口 2）上监听鼠标每 2 秒发送一次的 5 字节输入报告 `03 MM 40 ST LL`：`MM` 为型号代码，`ST` 为 `01`（电池供电）或 `02` / `03`（外部供电），`LL` 为电量（代码 `0x10` 时以十为单位）。有些型号用 `41` 或 `43` 代替 `40`，8K 接收器 `1D57:FA65` 可能在其厂商集合 `FF00:0001` 上发送。只读取已知的型号代码（在真实鼠标上见到的，以及这些品牌通用网页驱动 bk-gmice.com 的型号表中的），并且连续两帧一致时才采用电量，因为每次连接都以虚假的 100% 开始。插着数据线的鼠标（`1D57:FA55`）会接管接收器槽位。参考 [attackshark-battery-windows](https://github.com/daeoxide/attackshark-battery-windows)、[Attack-Shark-Battery-KDE](https://gitlab.com/gabriel17166/Attack-Shark-Battery-KDE)、[HaloBattery 社区分支](https://github.com/ahmedkhursheed23/HaloBattery)、[OpenMouse](https://github.com/OpenMouse-Project/mouse-protocol) 和 [furycube-g3-linux-bridge](https://github.com/HeyDSN/furycube-g3-linux-bridge)。 |
| `providers/steelseries.rs` | 在服务接口上发送输出报告 `0x92` / `0xD2`（Aerox、Prime）或 `AA 01`（Rival），参考 [rivalcfg](https://github.com/flozz/rivalcfg)。Aerox 3 Wireless Gen 2 回复 `92/D2 状态 电量 00`（状态 `00` 为电池供电，`01` 为充电中，`02` 为已充满；电量 `FF` 表示暂不知道），休眠时回复 `40 FF 00 00`，参考 [rivalcfg#276](https://github.com/flozz/rivalcfg/issues/276)。 |
| `providers/oem_mouse.rs` | CompX 的 17 字节帧，各字节之和为 `0x55`，VXE 和 ATK（ATK HUB）、Pulsar、Lamzu、Scyrox、Kysona、G-Wolves、Corsair Sabre v2 Pro 以及 Areson（OemDrv）的配置工具都使用它。只发送 `GetPower`（`08 04 … 49`），并向需要的接收器发送连接询问（`08 03 … 4A`），因为有些接收器在被询问之前不出声，还有少数会用已关机鼠标的最后电量来回复。帧以输出报告发到 `FF02` 集合，或者以特性报告发送、在 `FF01` 集合上得到回复（Areson、Dareu、Endgame Gear）。回复中包含电量——以百分比表示，或（在 `25A7:FA4A`、`FA07`、`FA08` 上）以十个百分点为单位——以及充电标志。被许多型号共用的接收器按其产品字符串命名。参考 [OpenMouse](https://github.com/OpenMouse-Project/mouse-protocol)、Linux 驱动 `hid-pulsar`、[vxe-battery-tray](https://github.com/ivancacic/vxe-battery-tray)、[redragon-mouse-linux](https://github.com/rajchauhan28/redragon-mouse-linux)、[xm2we-linux](https://github.com/okms/xm2we-linux)、[HaloBattery](https://github.com/HeyOkay/HaloBattery)、[OpenLinkHub](https://github.com/jurkovic-nikola/OpenLinkHub) 和 [Wireless-Device-Battery-Monitor](https://github.com/krisgfx9/Wireless-Device-Battery-Monitor)（自行实现）。与鼠标的第一次通信会写入日志。 |
| `providers/aula_mchose.rs` | 向接收器 `3554:FA09` 以及 AULA F75 Max、MCHOSE 新款键盘和 VGN 的接收器的 20 字节集合 `FF02:0002` 发送输出报告 `13 4A 01 …`；回复中包含百分比电量和充电标志。MCHOSE 型号用 `13 05 01 …` 读取一次，并在 M HUB 的型号代码表中查找。键盘每 5 分钟才询问一次，因为询问可能会唤醒它。参考 [myfinder-device-battery](https://github.com/wushuai0802/myfinder-device-battery) 和 [Wireless-Device-Battery-Monitor](https://github.com/krisgfx9/Wireless-Device-Battery-Monitor)（自行实现）。第一次通信会写入日志。 |
| `providers/ajazz_mouse.rs` | 向接收器 `A8A5:2255` 或数据线 `A8A4:2255` 的 `FF01:0010` 集合，以及 MCHOSE G3 V2（`3837:4245`，数据线 `3837:418C`）发送输出报告 `55 30 A5 2E 2E …`；回复 `AA 30 …` 中包含百分比电量，以及一个 USB 供电时不为 0 的字节。厂商网页面板把请求写成 `55 30 A5 0B 2E 01 01`，第一种形式没有回应时会尝试这种形式。AJAZZ T520 Max（`A8A5:2266`，数据线 `A8A4:2266`）会先被询问型号（`55 52 01 00 1A`），只有回复中写明其固件时才读取；它在充电字节置位时报告的 100% 会显示为充电中、不显示电量，因为鼠标在电池充满之前就会报告 100%。参考 [ajazz-aj139-macos](https://github.com/werquess/ajazz-aj139-macos)、[OpenMouse](https://github.com/OpenMouse-Project/mouse-protocol) 和 [Wireless-Device-Battery-Monitor](https://github.com/krisgfx9/Wireless-Device-Battery-Monitor)（自行实现）。第一次通信会写入日志。 |
| `providers/sonix_keyboard.rs` | 向接收器 `0C45:FEFE`、`0C45:FDFD`、`0C45:FEFC` 和 `05AC:024F` 的 33 字节集合 `FF60:0061` 发送输出报告 `20 01 … 21`；回复 `20 01 00 LL` 中包含百分比电量，没有任何信息表明键盘是否在充电。固件不同的键盘（AJAZZ AK820 Max Plus、AULA F87 Pro V2、F99 MAX）对此回复 0，并在设备信息中给出电量（`AA 10 18`，回复 `55 10 …`）；第一种形式没有结果时会询问一次。键盘每 5 分钟询问一次，没有回应时每分钟一次。参考 [vigil-watt](https://github.com/evren-oct/vigil-watt)、[sonix-keyboard-studio](https://github.com/donglover69/sonix-keyboard-studio) 和 [Wireless-Device-Battery-Monitor](https://github.com/krisgfx9/Wireless-Device-Battery-Monitor)（自行实现）。第一次通信会写入日志。 |
| `providers/razer_peripheral.rs` | OpenRazer 的 90 字节特性报告：命令 `07 80`（电量 0–255）、`07 84`（充电），CRC 为第 2–87 字节的异或；transaction id 和回复延迟因型号而异，取自 OpenRazer 的表格。 |
| `providers/logitech.rs` | HID++：探测接收器的 1–6 号槽位（数据线连接的设备用索引 `0xFF`），查找电量特性 `0x1004` / `0x1000` / `0x1001` / `0x1F20` 和名称特性 `0x0005`；较老的设备使用 HID++ 1.0 寄存器 `0x0D` / `0x07`。参考 [Solaar](https://github.com/pwr-Solaar/Solaar)。 |
| `providers/headset.rs` | 在耳机的厂商 HID 通道上请求和回复，字节参考 [HeadsetControl](https://github.com/Sapd/HeadsetControl)，HyperX Cloud III Wireless 参考 [HyperHeadset](https://github.com/LennardKittner/HyperHeadset)，Corsair HS80 RGB Wireless 参考 [OpenLinkHub](https://github.com/jurkovic-nikola/OpenLinkHub)（自行实现）。Corsair Virtuoso XT / SE 和 HS80 RGB Wireless 通过 Corsair 的 Bragi 属性读取：`0x0F` 为以千分之一为单位的电量，`0x10` 为充电状态。SteelSeries Arctis Nova Elite、Sony INZONE Buds 以及 MCHOSE、FIFINE 和 VGN 耳机参考 [HaloBattery](https://github.com/HeyOkay/HaloBattery) 和 [Wireless-Device-Battery-Monitor](https://github.com/krisgfx9/Wireless-Device-Battery-Monitor)。与耳机的第一次通信会写入日志。Logitech G 耳机报告的是电压，用各型号的表格换算。 |
| `providers/devices/` | 下面的设备都是表格中的行：要与哪个 HID 集合通信，以及一个负责询问和解析回复的函数。两个提供者轮询这些表格（耳机和其他所有设备），少数放不进一行的设备系列在同一模块中有自己的提供者。全部只读，并依据协议事实编写；与每个设备的第一次通信会写入日志。 |
| `devices/hyperx.rs` | 在接收器自己的集合上发送 HyperX NGENUITY 的状态请求：报告 `0C`（Cloud III S），`52 01` / `50 02` 一对（Cloud Alpha 2、Pulsefire Haste 2），`46` / `51`（Pulsefire Haste Wireless、Dart），带电芯电压的特性报告 `FF`（Cloud Stinger Core，电量为估算值）。参考 [HyperHeadset](https://github.com/LennardKittner/HyperHeadset)、[HeadsetControl](https://github.com/Sapd/HeadsetControl)、[ngenuity-linux-cli](https://github.com/PMarinov1994/ngenuity-linux-cli)、[HyperBatteryMonitor](https://github.com/davidsantanaalves/HyperBatteryMonitor)、[open-pulsefire-haste](https://github.com/evan-razzaque/open-pulsefire-haste) 和 [hyperx_pulsefire_dart_reverse_engineering](https://github.com/santeri3700/hyperx_pulsefire_dart_reverse_engineering)。 |
| `devices/centurion.rs` | `FFA0:0001` 上的 Logitech Centurion 协议：找到接收器的桥接特性，通过它询问耳机的电量特性在哪里，读取百分比和充电状态。`FF32:0074` 上的 ASTRO A50 Gen 4 基座：`54` 表示耳机是否已连接或已放在基座上，`7C` 为电量。参考 [HeadsetControl](https://github.com/Sapd/HeadsetControl)、[Solaar](https://github.com/pwr-Solaar/Solaar)、[eh-fifty](https://github.com/tdryer/eh-fifty) 和 [AstroBar](https://github.com/nichtlegacy/AstroBar)。 |
| `devices/razer_audio.rs` | Razer 耳机，四种协议：带命令 `21` / `2A` 的 64 字节报告 `02`（BlackShark V2 HyperSpeed、V3、Kraken V4、Kraken Kitty V3 Pro），特性报告 `07`（BlackShark V3 X），特性报告 `FF`（BlackShark V2 Pro 2020），以及通过接收器发送的 Airoha 命令——读取时把接收器切换到 remote 模式，读完再切回，与 Synapse 的做法相同（BlackShark V2 Pro 2023、Barracuda Pro）。参考 OpenRazer 的 pull request、[HeadsetControl](https://github.com/Sapd/HeadsetControl)、[HaloBattery](https://github.com/HeyOkay/HaloBattery)、[razer-blackshark-v2-hyperspeed-webhid](https://github.com/justik13/razer-blackshark-v2-hyperspeed-webhid) 和 [razer-kraken-v4-pro-linux](https://github.com/RGBLizard/razer-kraken-v4-pro-linux)。 |
| `devices/usb_headsets.rs` | 在接收器的厂商集合上发送一次状态请求，通过回显的命令、长度和校验和匹配回复：通过输入报告 `07` 的 Airoha 接收器（Audeze、AKG、Skullcandy、Alienware）、Poly BT600、Jabra 的 GN 协议、EPOS、JBL、ASUS ROG、Fractal、MOONDROP。Sony PULSE 3D 接收器不接受请求，所以只监听它的状态报告。参考 [HeadsetControl](https://github.com/Sapd/HeadsetControl)、[HaloBattery](https://github.com/HeyOkay/HaloBattery)、[G-Helper](https://github.com/seerge/g-helper)、[jbl-quantum-battery](https://github.com/Visner-org/jbl-quantum-battery) 和 [Wireless-Device-Battery-Monitor](https://github.com/krisgfx9/Wireless-Device-Battery-Monitor)。 |
| `devices/asus.rs` | 在设备的厂商集合上发送一次请求（鼠标为 `12 07`，键盘为 `12 01`），回复中包含电量和充电标志；设备休眠时接收器回复 `FF AA`。在 ROG Omni Receiver 上先读取已配对设备列表，然后分别在各自的通道上读取鼠标和键盘。参考 [G-Helper](https://github.com/seerge/g-helper)、[rogctl](https://github.com/Humblemonk/rogctl)、[HaloBattery](https://github.com/HeyOkay/HaloBattery)、[OpenAzoth](https://github.com/albzO/OpenAzoth)、[rogdrv](https://github.com/kyokenn/rogdrv) 和 OpenRGB。 |
| `devices/corsair.rs` | 在接口 1 的 `FF42:0001` 集合上读取 Bragi 属性：先询问接收器哪些槽位已连接，再向每个已配对设备询问电量（以千分之一为单位）、充电状态和 product ID；数据线连接的设备自己回答同样的读取。无论是否运行 iCUE，设备都保持在硬件模式。参考 [ckb-next](https://github.com/ckb-next/ckb-next)、[OpenLinkHub](https://github.com/jurkovic-nikola/OpenLinkHub)、OpenRGB、[BatteryWatch](https://github.com/itayavra/batterywatch) 和 [Wireless-Device-Battery-Monitor](https://github.com/krisgfx9/Wireless-Device-Battery-Monitor)。 |
| `devices/compx_page.rs` | 鼠标的配置通道，64 字节特性报告：写入电量请求（页 `00`，命令 `83`；较老的 G-Wolves 鼠标使用更早的请求），并从同一报告读回回复。LAMZU 和 WLmouse 的共用接收器还会告知连接的是哪款鼠标。参考 [OpenMouse](https://github.com/OpenMouse-Project/mouse-protocol)、[mow](https://github.com/korkje/mow)、[GloriousBatteryMonitor](https://github.com/AwesomeTy18/GloriousBatteryMonitor) 和 [lamzu-battery](https://github.com/lavandiI/lamzu-battery)。 |
| `devices/keyboards.rs` | 在接收器的厂商集合上发送一次电量请求：Evision 的报告 `04` / 命令 `1A`（CHERRY、ATK、VGN / VXE、AJAZZ AK992、Akko 和 AULA 鼠标），Semico 的状态 `0E`，VIA 的自定义值，M HUB 的设备信息，Alienware 的 `0E A1`。每 5 分钟询问一次；已知询问会推迟键盘休眠的，每 35 分钟一次。参考 [HaloBattery](https://github.com/HeyOkay/HaloBattery)、[BatteryWatch](https://github.com/B1Chat/BatteryWatch)、[myfinder-device-battery](https://github.com/wushuai0802/myfinder-device-battery) 和 [Wireless-Device-Battery-Monitor](https://github.com/krisgfx9/Wireless-Device-Battery-Monitor)。 |
| `devices/mice_brands.rs` | 每个品牌各自的状态请求：写入后再读回的特性报告（VAXEE `0E`、Ninjutso / Sprime `05` 和 `06`、Endgame Gear `A1`），或由输入报告回复的输出报告（Cooler Master `46 81`、ZOWIE `A5 03`、ROCCAT `90 0A`、Finalmouse `04` / `05`）。参考 [mouse-battery-monitor](https://github.com/stuffz/mouse-battery-monitor)、[ninjutso-battery-tray](https://github.com/DrStopor/ninjutso-battery-tray)、[OpenMouse](https://github.com/OpenMouse-Project/mouse-protocol)、[eruption](https://github.com/eruption-project/eruption)、[HaloBattery](https://github.com/HeyOkay/HaloBattery) 和 [Wireless-Device-Battery-Monitor](https://github.com/krisgfx9/Wireless-Device-Battery-Monitor)。 |
| `devices/mice_platforms.rs` | 按厂商自己的工具或网页驱动的方式发送一次状态请求，通过回显的命令、ID 和校验和匹配回复：Keychron Launcher 的协议（先询问 Link 接收器配对了什么，所以只配了键盘的接收器不会列出鼠标），Telink 的 `51 06`（Machenike、Darmoshark），Pulsar，MCHOSE 的各代 M HUB，ATK 的 NearLink，MSI，AJAZZ AJ179，Delux，DAREU，Royal Kludge。参考 [OpenMouse](https://github.com/OpenMouse-Project/mouse-protocol)、[keychron-battery-dkms](https://github.com/csutcliff/keychron-battery-dkms)、[PulsarBattery](https://github.com/darthsoup/PulsarBattery)、[HaloBattery](https://github.com/HeyOkay/HaloBattery) 和 [Wireless-Device-Battery-Monitor](https://github.com/krisgfx9/Wireless-Device-Battery-Monitor)。 |
| `devices/passive_mice.rs` | 不发送任何内容：通过在两次轮询之间保持打开的只读句柄，监听鼠标自己发送的状态报告（Rapoo：`FF00:0002` 上的报告 `07` 或 `BB`；Incott：`FF05:0001` 上的报告 `09`）。参考 Rapoo Hub 网页驱动、[Device-Battery-Info](https://github.com/PyFlat/Device-Battery-Info)、[rapoo_battery](https://github.com/zbndev/rapoo_battery)、[OpenMouse](https://github.com/OpenMouse-Project/mouse-protocol) 和 [Wireless-Device-Battery-Monitor](https://github.com/krisgfx9/Wireless-Device-Battery-Monitor)。 |
| `devices/controllers.rs` | Windows 把这些 2.4 GHz 接收器显示为不带电池的有线 Xbox 手柄，所以用厂商软件发送的状态请求在接收器的厂商集合上询问电量。Steam Controller 会自己发送电量，只需监听。不发送任何会改变手柄模式的内容。参考 [SDL](https://github.com/libsdl-org/SDL)、Linux 驱动 `hid-steam` 和 `hid-nvidia-shield`、[HaloBattery](https://github.com/HeyOkay/HaloBattery) 和 [Wireless-Device-Battery-Monitor](https://github.com/krisgfx9/Wireless-Device-Battery-Monitor)。 |
| `providers/standard_hid.rs` | 从任何 USB HID 设备的特性报告中读取 Generic Device Controls / Battery Strength 字段（`06:20`）。 |
| `providers/playstation.rs` | 不发送任何内容：读取一个输入报告及其状态字节（DualSense 为 USB 下的 `data[53]` / 蓝牙下的 `data[54]`，DualShock 4 为 `data[30]` / `data[32]`），与 Linux 的 `hid-playstation` 相同。 |
| `providers/xinput.rs` | Windows：`XInputGetBatteryInformation`：4 档 → 近似百分比。跳过蓝牙手柄，它们的电量来自 Windows（低功耗蓝牙）或手柄自己的电池报告（经典蓝牙）。 |
| `providers/xbox_bluetooth.rs` | Windows：不发送任何内容。通过在两次轮询之间保持打开的只读句柄，在手柄集合上监听输入报告 `04`（Battery Strength，`06:20`）：第 7 位为开启，第 4 位为充电，第 3–2 位为供电方式（USB、电池、Play & Charge），第 1–0 位为 4 档之一。参考 [xpadneo](https://github.com/atar-axis/xpadneo) 和 [SDL](https://github.com/libsdl-org/SDL)。 |
| `providers/nintendo.rs` | Windows：不发送任何内容。读取完整输入报告（`30`、`31`、`21`）的头部：第 2 字节的第 7–5 位为 5 档之一，第 4 位为充电。参考 [Nintendo_Switch_Reverse_Engineering](https://github.com/dekuNukem/Nintendo_Switch_Reverse_Engineering)、[SDL](https://github.com/libsdl-org/SDL)、Linux 的 `hid-nintendo` 和 [HaloBattery](https://github.com/HeyOkay/HaloBattery)。 |
| `providers/apple_keyboard.rs` | Windows：通过 `HidD_GetInputReport` 获取的输入报告 `90`：`90 SS LL`，`LL` 为百分比电量，`SS` 的第 1 位为充电。参考 [WinMagicBattery](https://github.com/hank1101444/WinMagicBattery) 和 Linux 的 `hid-apple`。 |
| `providers/bluetooth/` | Windows：设备属性 `DEVPKEY_Bluetooth_Battery`（即“设置 → 蓝牙”中显示的值），仅在 `ConnectionStatus = Connected` 时读取。已连接的低功耗蓝牙设备优先读取它自己的电池服务，因为该属性经常过时：直接从设备读取电量（服务和特征来自 Windows 缓存，值不走缓存，不写入任何内容），有多个时取最低值，每个都显示在详细信息中（ZMK 分体键盘的两半，按描述符 0x2901 命名）。AirPods 和 Beats 耳机：左右耳机和充电盒的电量来自它们的近距离配对广播（Apple Continuity 类型 0x07），在这类耳机连接时由被动的 `BluetoothLEAdvertisementWatcher` 监听，并按型号（已配对设备的 product ID）与耳机匹配，取最近信号最强的一条。macOS：`system_profiler SPBluetoothDataType` 报告的已连接设备信息（与蓝牙菜单显示的相同），包括 AirPods 的左右耳机和充电盒；对于通过免提协议报告电量的耳机，使用 macOS 在电源列表中保存的电量（`IOPSCopyPowerSourcesByType`，电池小组件和 `pmset -g accps` 显示的也是它）。 |
| `providers/apple_mobile.rs` | macOS：通过数据线连接的 iPhone 和 iPad，使用访达所用的 MobileDevice 框架：在与 `lockdownd` 的会话中读取已信任这台 Mac 的设备的 `com.apple.mobile.battery` 域。从不配对，也从不通过网络访问设备。 |
| `src/hid/` | 所有提供者所依赖的 HID 层：Win32（`windows.rs`）或 IOKit（`macos.rs`）。在 Mac 上，每个设备的报告描述符会被拆分成 Windows 会列出的集合（`descriptor.rs`），并以 Windows 路径的形式命名，所以每个提供者都能原样在 Mac 上工作。 |
| `macos/` | Mac 应用：围绕内核的 SwiftUI 和 AppKit，内核由 `macos/core` 构建为静态库。手柄通过 Apple 的 GameController 框架读取。桌面小组件（`macos/Widget`）只读取应用为它们写入其文件夹的设备信息，从不直接与设备通信。 |

## 添加设备

只需在一个 HID 集合上回答一次请求的设备，就是 [`src/providers/devices/`](../../src/providers/devices) 中表格的一行：它的 ID、集合，以及一个负责询问和解析回复的函数。放不进一行的设备系列，则是 [`src/providers/`](../../src/providers) 中实现 `Provider` trait 的模块：轮询硬件，并说明下次何时轮询。更多关于代码的内容见 [development.md](../development.md)。
